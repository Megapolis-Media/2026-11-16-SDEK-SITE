# Выделенный сервер CDEK FM

Production: `cdek-fm.ru`, сервер `194.58.103.93`, Ubuntu 24.04, Docker Compose и существующий Nginx под ISPmanager.

## Как выпускается сайт

1. Изменения разработчика поступают в `dev` через PR, затем владелец сливает `dev → master` через merge commit.
2. `.github/workflows/deploy.yml` запускается при push в `master`. Ручной запуск разрешён только для `master`.
3. GitHub Actions собирает образ `cdek-fm:<полный SHA коммита>`. При сборке выполняются тесты серверного хранилища, TypeScript и production-сборка.
4. Образ передаётся через SSH пользователю `cdek-deploy`. Его ключ разрешает только запуск root-owned скрипта `/usr/local/sbin/cdek-fm-deploy`; интерактивный shell, SFTP и forwarding для этого ключа отключены.
5. Скрипт сериализует выкладки через `flock`, останавливает предыдущий контейнер, делает резервную копию данных, применяет миграции и ждёт успешного healthcheck. На время смены версии возможен короткий перерыв.

В environment `production` репозитория настроены Secrets `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS` и Variables `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PORT`. Закрытый ключ не коммитится. Изменения скрипта выкладки и серверного Compose-файла устанавливаются администратором отдельно: код из репозитория не может самостоятельно заменить привилегированный скрипт сервера.

## Запуск и данные

Серверная сборка сохраняет приложение vinext/React и использует Node.js 24 LTS. Для неё `CDEK_RUNTIME=node` выбирает SQLite и файловое хранилище вместо привязок Cloudflare D1/R2. Изначальный режим Cloudflare остаётся доступен через прежние команды.

```sh
npm run install:ci
npm run test:server
npm run build:server
# Выберите локальный каталог данных, не production-каталог.
CDEK_DATA_DIR=./work/local-server-data npm run migrate:server
CDEK_DATA_DIR=./work/local-server-data npm run start:server
```

Контейнер работает от UID 1000, без дополнительных capabilities, с read-only файловой системой. На хосте открыт только loopback-порт `127.0.0.1:3101`, публичные запросы принимает Nginx. `/api/health` проверяет доступность схемы базы.

- `/srv/cdek-fm/data/cdek.sqlite` — база; файлы WAL/SHM находятся рядом.
- `/srv/cdek-fm/data/uploads/` — картинки чата.
- `/srv/cdek-fm/runtime.env` — закрытая конфигурация окружения, права `600`.
- `/srv/cdek-fm/backups/` — резервные копии перед выкладкой. Их нужно дополнительно копировать за пределы сервера и контролировать свободное место; автоматическое внешнее резервирование пока не настроено.
- `/srv/cdek-fm/.release` — имя успешно выпущенного образа.

Миграции фиксируются с контрольной суммой и выполняются транзакционно. Уже применённые SQL-файлы менять нельзя. Это новая база: перенос существующих данных из другого окружения выполняется отдельно.

## Админка и HTTPS

Вход в `/admin` — по логину `megapolis` и паролю. Начальные данные доступа доступны владельцу сервера в закрытом файле `/root/cdek-fm-admin-password`. В `runtime.env` хранится только scrypt-хеш пароля. Заголовки авторизации ChatGPT в серверном режиме игнорируются; вход через ChatGPT в этом режиме отключён.

Административная cookie имеет флаг Secure, поэтому для входа требуется HTTPS. Для сертификата нужно направить A-запись домена на новый сервер и проверить, что AAAA-запись не ведёт на другой сервер. До переключения DNS сайт можно проверять запросом с нужным Host к новому IP. Nginx не должен пропускать клиентские заголовки `Oai-Authenticated-*` и обязан сам выставлять адрес клиента и протокол.

TLS обслуживает существующий Nginx. Сертификат Let's Encrypt покрывает `cdek-fm.ru` и `www.cdek-fm.ru`. Certbot использует webroot `/var/www/cdek-acme` и systemd timer `certbot.timer`; deploy-hook `deploy/renew-nginx.sh` проверяет конфигурацию и перезагружает Nginx после продления. Прямой HTTP-запрос к IP возвращает 404, а HTTP по домену перенаправляется на HTTPS. Для других сайтов добавляются отдельные виртуальные хосты с их доменами и loopback-портами; DNS связывает домен с IP, Nginx выбирает приложение по имени домена.

## Проверка и откат

На сервере:

```sh
cd /srv/cdek-fm
export CDEK_IMAGE="$(cat .release)"
docker compose ps
docker compose logs --tail=100 web
curl --fail http://127.0.0.1:3101/api/health
```

При неудаче выкладки скрипт пытается поднять предыдущий образ. База автоматически назад не откатывается: это предотвращает потерю записей, сделанных новой версией. Миграции должны сохранять совместимость с предыдущим релизом. Разрушительные изменения схемы требуют отдельного плана и окна обслуживания.

Для ручного отката администратор задаёт `CDEK_IMAGE=cdek-fm:<SHA предыдущего коммита>` и запускает `docker compose up -d --wait`. Проверяет healthcheck, затем обновляет `.release`. Восстановление базы из резервной копии — отдельная операция при остановленном приложении, с предварительным сохранением текущих данных.

Гипервизор, мониторинг, перенос прежней базы и автоматическая выгрузка бэкапов за пределы сервера в этот этап не входят.
