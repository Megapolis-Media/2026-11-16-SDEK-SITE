# Техническая поддержка CDEK FM

Кнопки в плеере и под чатом открывают одну форму. После отправки посетитель получает номер заявки, а редакция видит email, описание, статус и состояние доставки в `/admin#support`. Адрес для копий задаётся там же, в разделе «Доставка заявок». Чтобы отключить копии, очистите поле и сохраните его.

## Подключение доставки

Примените миграцию `drizzle/0004_support_tickets.sql` по инструкции для вашей среды. Для SQLite используется `npm run migrate:server`, для D1 — [инструкция работы с миграциями](CDEK-FM.md).

Для выделенного сервера задайте значения в закрытом `runtime.env`, для Worker — в переменных и секретах среды. Локально используйте `.dev.vars`. Токены helpdesk и API задаются независимо и должны содержать от 32 до 256 символов без пробелов и запятых.

| Переменная | Назначение |
| --- | --- |
| `CDEK_SUPPORT_RESEND_KEY` | Ключ Resend для отправки почтовых копий. |
| `CDEK_SUPPORT_EMAIL_FROM` | Email отправителя с подтверждённого в Resend домена. Ответ на письмо адресуется автору заявки. |
| `CDEK_SUPPORT_HELPDESK_URL` | HTTPS-адрес, на который helpdesk принимает новые заявки. |
| `CDEK_SUPPORT_HELPDESK_TOKEN` | Bearer-токен, который проверяет получатель webhook. |
| `CDEK_SUPPORT_API_TOKEN` | Отдельный Bearer-токен для запросов от helpdesk к CDEK FM. |

Сайт сначала сохраняет заявку и только затем параллельно передаёт её настроенным получателям. У каждой доставки свой статус. При недоступности получателя заявка остаётся в ленте. Кнопка «Повторить доставку» повторяет каналы, которые ожидают отправки или завершились ошибкой. Если отправка прервалась на сервере, повтор возможен через 30 секунд. Подключив каналы после запуска, редакция может отправить ранее поступившие заявки из ленты, а helpdesk может забрать их по API.

## Webhook для новых заявок

CDEK FM отправляет `POST` с `Content-Type: application/json`, `Authorization: Bearer <токен webhook>` и `Idempotency-Key: cdek-fm-support/<ticket.id>`. Тело содержит `event: "ticket.created"`, `source: "cdek-fm"` и объект `ticket` из примера ниже. При поступлении webhook создайте карточку в колонке новых заявок и сохраняйте `ticket.id` как внешний ID. Возвращайте `2xx` после сохранения карточки. Повтор того же ID должен возвращать `2xx` без создания новой карточки. Получатель должен принимать запросы без переадресации.

## API helpdesk

Запросы используют `Authorization: Bearer <токен API>`. Выполняйте их с сервера helpdesk, чтобы токен оставался закрытым.

| Запрос | Ответ |
| --- | --- |
| `GET /api/support/integration?after=0&limit=50` | `{ tickets, nextAfter, hasMore }`, заявки по возрастанию номера. Передавайте `nextAfter` в следующий запрос. Максимальный `limit` — 100. |
| `GET /api/support/integration?id=<UUID>` | `{ ticket }` с актуальным статусом заявки. |
| `PATCH /api/support/integration` | Обновляет статус. Тело JSON содержит `id`, `status` и последнее значение `updatedAt`. Ответ содержит `{ ticket }`. |

```json
{
  "id": "b0fb9a19-20df-424d-afd7-f6c90a2709fa",
  "number": 1,
  "email": "listener@example.com",
  "description": "Не запускается радио",
  "status": "new",
  "createdAt": 1794902400000,
  "updatedAt": 1794902400000
}
```

Статусы `new`, `in_progress` и `resolved` соответствуют новым, взятым в работу и решённым заявкам. Время передаётся в миллисекундах Unix. Если заявку успел изменить другой редактор, API возвращает `409` с актуальным `ticket`. Загрузка по курсору дополняет webhook и позволяет импортировать пропущенные заявки. Для уже известных заявок используйте запрос по ID для сверки статуса.
