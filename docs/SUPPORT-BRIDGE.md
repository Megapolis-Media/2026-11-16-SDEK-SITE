# Центральная поддержка CDEK FM

Текущая форма подключается к продукту Websites платформы Megapolis Support. Тикеты и переписка хранятся в центральной платформе. Backend CDEK FM предоставляет same-origin мост `/support-api/*`; браузер не обращается к платформе с интеграционным ключом. Старая локальная очередь и её административный API сохраняются отдельно, без автоматического переноса истории или скрытой подмены ошибки доставки локальной заявкой.

В разделе «Техподдержка» админки CDEK FM показан один список заявок центральной платформы со всеми статусами. Общая кнопка открывает https://help.megapolis.media/websites/support, а ссылка в карточке — конкретный тикет. Подключение сайта интеграционным ключом не заменяет авторизацию сотрудника поддержки. Отдельные локальный архив и настройки доставки убраны из интерфейса; прежние данные и backend API не удаляются.

## Конфигурация

Только в закрытом `/srv/cdek-fm/runtime.env` (права 0600), не в Git и не в `NEXT_PUBLIC_*`:

```dotenv
CDEK_SUPPORT_PLATFORM_URL=https://help.megapolis.media/websites/api/v1
CDEK_SUPPORT_PLATFORM_KEY=<отдельный ключ интеграции CDEK FM>
CDEK_SUPPORT_SITE_ORIGIN=https://cdek-fm.ru
```

Публичный API платформы имеет префикс `/websites/api/v1`; вариант без `/websites` здесь не работает. Origin сайта задаётся сервером, а не заголовками посетителя. Гостевые посетители канонического сайта и `www` используют одинаковую серверную интеграцию; их first-party cookies остаются отдельными.

После миграций, запуска образа с новой конфигурацией и доступности HTTPS выполнить на сервере:

```sh
cd /srv/cdek-fm
docker compose exec -T web node scripts/register-support.mjs
```

Регистрация идемпотентна. Платформа обращается к `/.well-known/support-bridge.json?challenge=...` и проверяет HMAC-SHA256: ключ подписи — hex-строка SHA256 API-ключа, сообщение — `challenge + '\n' + origin`. Скрипт завершится успешно только при `status=healthy` и заполненном `verifiedAt`. До выпуска нового endpoint домен может иметь состояние `unreachable`; одна запись в реестре не означает работающего подключения. Повторную проверку также может вызвать редактор через `POST /support-api/register` с действующей сессией админки CDEK FM и своим Origin.

## Посетитель и переписка

Гость указывает имя, описание и необязательный email для связи. Email добавляется к тексту обращения и передаётся отдельным валидированным полем `contactEmail`; он не является доказательством личности. Поддержка отвечает в переписке на сайте. Подтверждение создания тикета на email должно отправляться самой платформой поддержки. Текущая версия её `/api/v1/tickets` ещё не обрабатывает `contactEmail` и не ставит посетительские подтверждения в очередь: она отправляет уведомления сотрудникам. До добавления этой функции платформа видит email в тексте, а сайт не сообщает об отправленном письме. SMTP на CDEK FM для этого не настраивается.

Непрозрачный гостевой credential хранится в сессионной cookie `__Host-cdek-support`, `Secure; HttpOnly; SameSite=Lax; Path=/`, без `Max-Age` и `Expires`. Это доступ в браузерном сеансе, а не регистрация или годовая авторизация; поведение восстановления сеанса зависит также от браузера. Обычные ответы браузеру содержат только разрешённые поля гостя, тикета и клиентских сообщений. В интерфейсе нет поля или кнопки кода восстановления. Внутренняя эскалация не выдаётся. Подмена `externalUserId`, автора или номера посетителя в теле запрещена. Подключение аккаунтов сайта не реализуется: CDEK FM работает в гостевом режиме.

В окне доступны список прежних обращений, создание нового, сообщения и статус. Опрос — пять секунд при открытом окне и активной вкладке; в скрытой вкладке запросы не выполняются до проверки видимости, при ошибках действует backoff до минуты. Запросы одного окна не перекрываются; страницы сообщений дочитываются сразу по возрастающему курсору. Закрытие окна отменяет клиентские запросы, повторная загрузка восстанавливает историю через cookie. Идентификаторы создания заявки и сообщения сохраняются при повторе после сетевой ошибки, чтобы избежать дубликатов.

Технические методы восстановления оставлены для совместимости протокола платформы, но пользовательский интерфейс их не вызывает и не показывает credentials. Выход очищает cookie текущего устройства. После утраты браузерного сеанса автоматическое восстановление через введённый email не обещается; подтверждение адреса и доступ по email — отдельная задача платформы. Серверный `POST /support-api/session/forget` отзывает гостя на платформе. При ротации интеграционного ключа ошибка `INTEGRATION_UNAUTHORIZED` не очищает гостевую cookie; после настройки нового ключа и подтверждения домена история снова доступна в том же сеансе.

## Защита и ограничения

Нужна миграция `0007_support_bridge.sql` перед запуском. SQLite хранит только счётчики частоты запросов моста. Создание/восстановление гостя ограничено 30 запросами в минуту с сетевого адреса, действующая сессия — 120 в минуту, общий предел — 1200 в минуту. Лимиты самой платформы также действуют. POST требует своего Origin; `Sec-Fetch-Site` от чужого сайта отклоняется. Таймаут upstream — 10 секунд, без redirect, максимум ответа 1 МиБ, входа — 24 000 байт. Текст отображается средствами React без HTML-вставок.

Интеграция текстовая: фотографии эфира и их квота не относятся к вложениям поддержки. API платформы не предоставляет файловые вложения. Утрата cookie и кода без регистрации не позволяет автоматически опознать гостя; очистка cookies не удаляет серверные обращения.

HTTP smoke проверяет маршруты в самостоятельном собранном приложении.

Дополнительно выполнен локальный сквозной тест с настоящим API из `support-mediacenter` и отдельной базой в памяти: регистрация, сессия, заявка, ответ оператора, сообщение посетителя, повторные отправки, выход, восстановление и запрет доступа другому гостю. В браузере проверены создание заявки, получение ответа, отправка сообщения, перезагрузка, выход и восстановление по коду. Эти проверки не создают рабочих обращений. Production-приёмка после выпуска должна отдельно подтвердить проверенный домен и цикл с оператором на действующей платформе.

## Заявки в админке CDEK FM

Раздел «Техподдержка» получает карточки из центральной платформы: номер, тема, имя отправителя, статус, дата создания и ссылка на конкретный тикет. По умолчанию показаны все статусы, включая закрытые; есть фильтр, постраничная загрузка по 30 заявок и автоматическое обновление каждые 15 секунд в открытой вкладке. При недоступности платформы выводится ошибка; ранее загруженные карточки помечаются как последние полученные данные.

`GET /api/admin/support/central` требует действующую авторизацию редакции CDEK. Сервер обращается к `GET /websites/api/v1/site/tickets` с закрытым ключом и настроенным `CDEK_SUPPORT_SITE_ORIGIN`; посетительская cookie для этого не используется. Ключ, origin и адрес платформы нельзя выбирать параметрами браузера. API платформы проверяет принадлежность подтверждённого включённого домена ключу и возвращает только метаданные его заявок, без сообщений, внутренних заметок и credentials. Отозванный ключ больше не даёт доступа. Данные не кэшируются.

Переход `https://help.megapolis.media/websites/support#tickets&ticket=<id>` открывает нужный тикет и требует штатного входа сотрудника поддержки. Статус меняется на платформе и появляется в карточке после обновления. В интерфейсе используется только единый центральный список, без отдельной локальной очереди.

Для выпуска этой функции сначала требуется версия платформы с `/api/v1/site/tickets`, затем версия сайта с новым proxy и карточками. Миграция заявок и изменение схемы БД не нужны: список включает уже созданные обращения. Проверки безопасности включают изоляцию разных origin на одном ключе, чужой ключ, отключённый домен, отозванный ключ и отсутствие редакционной сессии.

## Проверка локального сайта с рабочей платформой

Исходящий HTTPS-запрос из локального backend не требует публичного адреса, туннеля или изменения DNS. Однако рабочая платформа отдельно требует подтверждения зарегистрированного origin. Для `https://cdek-fm.ru` до выпуска публичного проверочного endpoint запрос создания сессии вернул HTTP 503: «Сайт ещё не подтвердил регламент интеграции; выполните проверку домена». Это ответ политики платформы, а не ошибка соединения. Новая копия ключа сама по себе этого требования не отменяет.

Мост передаёт сбой upstream как HTTP 502 с сообщением о временной недоступности, сохраняя гостевую cookie и введённые данные. Поведение дополнительно проверено регрессионным тестом. После production-выпуска публичный origin подтверждён штатной проверкой, без отключения защиты, изменения DNS или внешнего туннеля.
